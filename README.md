# Сборщик конфигов

Отдельный публичный репозиторий, который раз в час сам собирает конфиги из открытых
источников, проверяет их и публикует только то, что живо. Приложение читает готовый файл —
и не тратит трафик и батарею телефона на проверку сотен серверов.

Почему это вынесено наружу: раньше телефон получал 300 конфигов и находил среди них 10–15
рабочих. Работу по отбраковке делал пользователь, своим соединением. Здесь она бесплатна.

## Как устроено

`sources.txt` — список источников. Единственный файл, который вы правите руками.

`collect.py` — конвейер:

1. **Сбор.** Скачивает все источники. Формат не важен: текст, base64, JSON — ссылки
   вытаскиваются по образцу, а не разбором строк, поэтому новый формат ничего не ломает.
2. **Дедупликация.** Схлопывает конфиги, одинаковые по сути. В публичных списках один сервер
   лежит десятком копий, различающихся только отпечатком клиента (`fp`) и именем. Из группы
   остаётся один — с предпочтением `firefox`, `chrome` последним: он самый массовый и его
   чаще распознают.
3. **Отсев непригодных.** Убирает то, что ядро приложения отказывается запускать: VLESS без
   TLS/Reality и без своего шифрования, Trojan без TLS, конфиги с `allowInsecure`. Это важно
   не косметически — один такой участник в балансировщике роняет всю группу целиком.
4. **Проверка доступности.** TCP-подключение к каждому уникальному адресу (не к каждому
   конфигу). Hysteria2 работает по UDP, для него TCP-проверка бессмысленна — такие конфиги
   проходят дальше, но с худшей оценкой, чтобы не оказаться выше реально проверенных.
5. **Страна.** Один пакетный запрос на сто адресов вместо ста запросов — на телефоне мы
   упирались в лимиты бесплатного сервиса.
6. **Публикация.** Лучшие по задержке, не более 8 на страну, с именами вида `Нидерланды 3` —
   в том виде, в котором приложение группирует их в балансировщики.

Результат: `configs/best.txt` (для приложения) и `configs/best.json` (чтобы можно было
глазами посмотреть, что произошло в этом прогоне).

Зависимостей нет — только стандартная библиотека Python.

## Что нужно сделать один раз

1. Создать **публичный** репозиторий на GitHub. Публичный принципиально: для публичных
   репозиториев Actions бесплатны без ограничения по минутам, для приватных — 2000 минут в
   месяц. Секретов здесь нет, скрывать нечего.
2. Положить в него содержимое этой папки (`collect.py`, `sources.txt`,
   `.github/workflows/collect.yml`, этот файл).
3. Открыть вкладку Actions, разрешить запуск, нажать **Run workflow** — первый прогон вручную,
   чтобы сразу увидеть в логах, сколько собралось и сколько ответило.
4. Прислать имя репозитория — я добавлю ссылку на результат в манифест на Netlify, и
   приложение начнёт брать конфиги оттуда.

Дальше он работает сам.

## Подводные камни, о которых стоит знать заранее

**Расписание не точное.** GitHub запускает cron с задержкой, иногда в несколько минут. Для
часового интервала это неважно.

**Прогон отменяется, если репозиторий 60 дней без активности.** Нас это не касается: job сам
коммитит результат, и это считается активностью.

**Публикация может отказаться сработать.** Если прогон дал ноль конфигов или меньше четверти
от прошлого количества, скрипт выходит, не перезаписав файл. Приложение заменяет список
целиком, поэтому обрубок дошёл бы до всех пользователей сразу; прошлый список хотя бы вчера
работал.

**Скорость пока не измеряется.** Сейчас конфиги сортируются по задержке отклика, а она почти
ничего не говорит о пропускной способности — полные полоски при копеечной скорости мы уже
видели. Реальный замер (скачивание 3 МБ через каждый сервер) добавлю следующим шагом, когда
этот этап отработает вживую. Тащить два новых механизма в один заход не стоит: если что-то
не заработает, будет непонятно, что именно.
